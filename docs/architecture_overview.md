# Architecture Overview
<!-- doxygen-label: arch_overview -->

This page gives a contributor-oriented map of the Home IO Control component and links the generated API documentation back to the main architectural layers.

## Layer Map

- [Protocol Layer](https://laberning.github.io/home_io_control/group__hioc__protocol.html): frame layout, command builders, cryptographic helpers, and shared protocol utilities. The protocol model is split into cohesive headers (`proto_sizes.h`, `proto_timing.h`, `proto_constants.h`, `proto_device_kinds.h`, `proto_device_model.h`, `proto_device_features.h`, `proto_device_types.h`, `proto_codecs.h`, `proto_private_registers.h`, `proto_commands.h`, `proto_crypto.h`) with `proto_frame.h` holding only the frame container and `proto_device_types.h/.cpp` holding the one node-type / subtype table every name, entity class, platform and behaviour flag is read from, with `proto_device_features.h` defining the capability bits each row carries and `proto_device_types.h` also holding the named-position table and the main-parameter value check, and `proto_device_kinds.h` holding the kind enums (`DeviceType`, `DeviceModel`, `DeviceCapabilityClass`, `CoverCommand`) and their name functions with no codec behind them, and `proto_device_model.h/.cpp` holding `IoDevice::features` with the one resolver, `resolve_device_features()`, that `DeviceRegistry` runs whenever a record is stored or learns its type ([ADR 0052](adr/0052-device-types-follow-the-io-node-type-and-subtype-table.md)); every capability decision reads the row's feature word through `device_features()` (the subtype-58 rule is one function, `main_parameter_only_variant()`), every named position is one `NAMED_POSITIONS` entry, and the row's `EXPERIMENTAL` flag marks a kind no capture or report has confirmed ([ADR 0059](adr/0059-device-capabilities-come-from-the-type-table.md)); `proto_private_registers.h/.cpp` holding the transport of the private register protocol (the four-byte request header, the read request and the echo check) that both the heater and the hot water codec build on; `proto_heating.h/.cpp` holding the heater register table and `proto_heating_profiles.h/.cpp` the heating profiles that decide what a climate card offers per heater kind and how it is commanded and polled, with `plan_heating_write()`, the pure function that turns one climate request into a register write, a heating level or a temperature EXECUTE and says whether the register is read back, and `reduce_heating_card()` and `command_heating_card()`, the pure functions that compute what the climate card shows (mode, preset, action, temperatures) from the heater's readings and from an accepted command ([ADR 0054](adr/0054-heaters-are-read-back-over-the-private-register-protocol.md), [ADR 0055](adr/0055-a-climate-entitys-traits-come-from-the-devices-heating-profile.md)); `proto_dhw.h/.cpp` holding the domestic hot water codec — its big-endian family-0x00 registers, the mode and duration writes, the operating-mode word that carries boost and away, and the target on the main-parameter scale ([ADR 0068](adr/0068-a-domestic-hot-water-device-is-a-water-heater.md), [ADR 0081](adr/0081-a-water-heaters-boost-and-away-travel-in-the-operating-mode-word.md)); each header's includers name their real dependencies directly rather than relying on an umbrella.
- [Radio Driver Layer](https://laberning.github.io/home_io_control/group__hioc__radio.html): the `RadioDriver` abstraction and the SX1276 / SX1262 / LR1121 implementations. Chips without hardware IoHomeOn framing (SX1262 and LR1121) share the software PHY in `radio_soft_phy.h/.cpp` (UART bit-encoding for TX, UART-decode probe with CRC validation for RX) and the IRQ-driven RX/TX orchestration in `SoftPhyDriverBase` (`radio_soft_phy_driver_base.h/.cpp`), which `RadioSX1262`/`RadioLR1121` both derive from — SPI opcode encoding/transport and IRQ bit values/word width stay behind virtual primitives each chip implements. The LR1121 driver is hardware-validated: authenticated 2W exchanges (open/close/stop with real position/state feedback) confirmed against a real Somfy Sunea IO awning motor.
- [Controller Layer](https://laberning.github.io/home_io_control/group__hioc__hub.html): `IOHomeControlComponent` orchestrates setup and loop scheduling through fourteen collaborator objects (fifteen when `lr1121_firmware_update:` is configured) — `ExchangeEngine` (authenticated exchanges, the shared `listen()` primitive every radio wait — its own and `PairingEngine`'s — runs through, and `run_attempts()`, the loop of tries with the gap, watchdog feed and optional budget that `PairingEngine`'s retry loops run through; `send_and_receive()` takes one `ExchangeOptions` value (a try count or a read kind, preamble override, key), plans the exchange once and shares the same step before each try), `PairingEngine` (discovery and pairing; it builds two parts of its own, `KeyPull`, which asks a device that hands out its own key for it and has it prove it holds it, and `KeyHolderSearch`, which finds the devices that hold a pulled or returned key with a heater probe and a roll-call and registers them; neither holds a hub pointer), `ManagementActions` (the native API actions — rename, identify, force-open, scan paired devices, the two one-way actions and heating control — and the owner of `DiagnosticProbes`, the opt-in probe collaborator that holds no hub pointer, only three injected calls: [ADR 0072](adr/0072-diagnostic-probes-are-their-own-collaborator.md)), `HeaterController` (heating and hot water: the register heater's writes and register reads, the level and temperature heaters' EXECUTEs, the water heater's target, mode, boost and away writes with their read-backs, `execute_heating_plan()` (the one entry point that sends a planned climate write and reads the register back), the regular polls of all heaters and water heaters with their backoff ladder, and the stateless decoding of their status answers in `heater_controller_status.cpp`; like `DiagnosticProbes` it holds no hub pointer, only injected calls, but its status read goes through the hub's status decoder: [ADR 0083](adr/0083-heating-and-hot-water-live-in-their-own-collaborator.md)), `DeviceRegistry` (device table, callbacks, and the feature resolution of every record it stores), `OperationQueue` (pending-operation coalescing), `StatusPollPolicy` (per-device poll scheduling), `PeriodicPollPolicy` (the schedule and miss counter of each opt-in periodic poll: rain, sun level, battery level and the cover status refresh at rest; one instance per poll), `roll_call.h/.cpp` (the keyed roll-call sweep — frame shapes, channels, reply decoding and de-duplication — that Scan Paired Devices runs once per distinct key, with the scan and key-pull reports built from what it found, and any collaborator that needs "who answers under this key?" can run), `device_yaml_snippet.h/.cpp` (the paste-ready ESPHome YAML for a device and the ESPHome platform each device kind maps to, used by roll call and pairing; the protocol layer holds no integration text), `PairingTelemetry` (per-attempt pairing event recorder, shared with both engines; its read-only companion `pairing_advisor.h` turns a completed attempt into actionable diagnostics), `OneWayTransmitter` (1W command bursts — the one radio-driving collaborator that awaits nothing), `KeyExtractionResponder` (the impure half of the "Recover System Key" feature), `OnewayKeyAdoption` (receive-only 1W controller-key adoption), `OneWayReceiver` (the receive-side state of overheard 1W frames: the burst window that holds background polls back, the duplicate filter that collapses a remote's repeats into one press, the pairing-gesture sighting `PairingEngine` seeds its telemetry with, the sender allowlist, and up to four 1W frames an exchange's wait heard and ignored, which the hub takes at the top of its next `loop()` pass and handles at their arrival times like an idle frame; it holds no hub pointer and calls nothing, the hub feeds it each frame and keeps what needs the registry or the API: following a linked remote and firing the sender event), `DeviceEventLog` (the count, text and subscriber behind the "Last Device Event" sensor), and — compile-gated — `Lr1121FirmwareUpdateController` (LR1121 flash orchestration). The hub itself is split by concern: `hub_core.cpp` (lifecycle and loop), `hub_operations.cpp` (queued operation dispatch), `hub_status.cpp` (passive receive-side handling, which hands a heater's or water heater's status answer to the controller's decoders), plus a thin `hub_pairing.cpp` wrapper around `PairingEngine` (the forwarders to `HeaterController`, `KeyExtractionResponder` and the other collaborators that an entity port or the firmware reaches are inline one-liners on `IOHomeControlComponent`; the native API actions that `ManagementActions` registers, management and probe actions alike, call it directly; the hub only starts that registration). The `decisions_*.h` headers (exchange, channel, attempts, pairing, oneway, status) hold the pure frame-classification and planning helpers, testable without radio or timing. The "Recover System Key" key-extraction responder is `PairingEngine`'s device-role mirror: where `PairingEngine` drives the hub *pairing to* a device (blocking, one call per attempt), `pairing_responder.h/.cpp` is event-driven and stateless-per-call — its pure ARMED_IDLE→SENT_DISCOVER_RESP→SENT_CONFIRM_ACK→SENT_CHALLENGE→EXTRACTED transitions are invoked for the 0x28/0x2C/0x31/0x32/0x36/0x3C frames through `KeyExtractionResponder::try_handle_frame()`, which `process_received_packet_()` (`hub_status.cpp`) calls for every received frame, while the hub keeps operating normally; the impure side (arming, throwaway node-ID generation, the auto-off timer, and the security log block) lives in the `KeyExtractionResponder` collaborator (`key_extraction_responder.h/.cpp`). Hardware-confirmed end to end against a VELUX KLR200 and a Somfy TaHoma — see [Key extraction](key-extraction.md).
- [Tuning Layer](https://laberning.github.io/home_io_control/group__hioc__tuning.html) (sub-group of the Controller Layer): the runtime `TuningConfig`, the table-driven `tuning_registry`, and the optional Home Assistant number/select entities.
- [ESPHome Integration Layer](https://laberning.github.io/home_io_control/group__hioc__entities.html): the runtime entities plus the Python schema/codegen modules that expose the component to ESPHome. Shared device-binding codegen lives in `platform_common.py`: a platform declares its companion entities as a table of (id key, id suffix, class, condition) rows that `inject_companion_ids()` turns into IDs at validation time, and `create_companion()` builds each one in `to_code()` from its schema. The module also holds the helpers that read the Python mirror of the capability word (`require_feature()` for keys a kind cannot use, `warn_if_experimental_kind()` for the config-time warning); the mirror itself is `DEVICE_FEATURES` in `hub_validators.py`, kept equal to the C++ table by a sync test; the C++ counterparts are three mixins in `platform_entity_base.h` — `DeviceBoundEntity` for the main entity platforms (it registers the device, delivers only that device's updates to the entity's handler, and offers the shared setup gate for a declared kind the entity cannot drive; a cover's or light's own settings reach the registration through a configuration hook, and the Home Assistant fraction to device position conversion is `io_from_fraction()` / `fraction_from_io()` in `entity_helpers.h`), `DeviceBoundCompanion` for the per-device entities that do not own the device (the auto-generated companion diagnostic sensors — device name, active issue, RSSI, last contact, exchange failures, unconfirmed exchanges, last commanded by, last command source — and the cover command buttons — favorite/vent — plus the silent-operation switch, the travel-speed select, the rain binary sensor, and the sun level and battery sensors), and `HubBoundEntity` for the hub-level control entities that need only the control port. Entities reach the hub only through the three ports of `hub_ports.h` ([ADR 0084](adr/0084-entities-reach-the-hub-only-through-ports.md)): `HubDevicePort` (register a device, read its record, follow its updates, queue commands and status reads, poll intervals, optimistic state) for the device-bound entities and companions, `HubHeatingPort` (register reads and writes, executing a heating write plan, the water heater's settings) for the climate and water heater entities and their controls, and `HubControlPort` (pairing, scanning, the arming switches, one-way sending and reporting, device event and pairing result text, the LR1121 update) for the hub-level entities. The mixins hold port pointers, never the hub class, and their `set_parent(hub)` takes from whatever it is given each port that object implements, so the generated code is unchanged and a test passes a double of the ports instead of a hub. The tuning number/select entities keep their own constructor-injected parent to avoid pulling `hub_core.h` into their header.

## Layering Rules

These invariants keep the layers independent; changes should preserve them:

1. The protocol layer is radio-agnostic: no chip names, chip registers, or driver behavior in `proto_*` files. `proto_timing.h` holds only chip-neutral protocol timing.
2. The controller layer is chip-agnostic: hub and engine code interacts with the radio exclusively through `RadioDriver` virtuals (`response_preamble()`, `preamble_bits_per_byte()` (every preamble is set as a duration and each driver converts it to bytes, [ADR 0097](adr/0097-every-preamble-is-set-as-a-duration-the-same-on-every-radio.md)), `hop_dwell_ms()`, `has_fast_tx_rx_turnaround()`, `run_idle_scan()`, `tx_air_time_us()`, `apply_tuning()`, …). Chip-specific behavior belongs in a driver override, not in an `if (chip == …)` branch; `chip_name()` is for logging only. What a transmission needs is stated in chip-neutral terms on `RadioTxConfig`: its channel, its preamble length, its clear-channel threshold ([ADR 0045](adr/0045-listen-before-talk-is-part-of-sending.md)) and its wake-up level (`TxWake`, derived once in `ExchangeEngine::transmit_frame()` from the frame's START bit and preamble), so a driver never has to infer intent from a preamble length. The driver in turn states how long a transmission takes (`tx_air_time_us()`) and how a channel reading is taken (`measure_channel_level()`, `cca_settle_us()`), so a request's channel access ([ADR 0096](adr/0096-the-hubs-requests-take-a-free-channel-and-are-never-forced-onto-a-busy-one.md)) reads the same on every chip, and the exchange engine starts a try only if that transmission ends inside the exchange budget ([ADR 0044](adr/0044-chip-neutral-transmit-intent-wake-level-idle-scanning-and-air-time.md)).
3. Chip-specific constants live either in the driver header (`radio_sx1276.h` / `radio_sx1262.h` / `radio_lr1121.h`) or, when they are user-tunable defaults, next to their `TuningConfig` fields in `tuning_config.h`.
4. The composition root is `hub_core.cpp` `setup()`: it is the only place that names concrete driver classes, selecting one by the required `radio_type` YAML field.
5. Include direction is enforced. Collaborators and entities never include the hub's private `hub_internal.h`; the entity platforms (`platform_*`) neither include `hub_core.h` nor reach it through another header, and use the hub only through the ports of `hub_ports.h`; only the hub's own files, the tuning entities and the management actions reach `hub_core.h`; protocol and radio files include only their own layer (and, for radio, the protocol layer). `make include-graph` fails when an entity file reaches `hub_core.h` or a file outside this list does.

## Request Flow

1. A YAML declaration is validated by the Python code-generation modules in [Python Code Generation](https://laberning.github.io/home_io_control/group__hioc__codegen.html).
2. ESPHome codegen wires those declarations to runtime C++ objects such as `IOHomeControlComponent`, `IOHomeCover`, `IOHomeLight`, `IOHomeLock`, `IOHomeSwitch`, `IOHomeFan`, `IOHomeClimate`, `IOHomeWaterHeater`, and the generated companions (`IOHomeDeviceNameTextSensor` per entity, `IOHomeDiscoverButton` and its `IOHomePairingResultTextSensor` when `home_io_control.discover_and_pair_button: true`, `IOHomeAcceptForeignPairingSwitch` (the "Recover System Key" switch) when `home_io_control.accept_foreign_pairing: true`, `IOHomeRecoverOneWayKeySwitch` when `home_io_control.recover_oneway_key: true`, `IOHomeScanPairedDevicesButton` when `home_io_control.scan_paired_devices_button: true`, `IOHomeDeviceEventTextSensor` when `home_io_control.diagnostic_probes: true`, `IOHomeLr1121FirmwareUpdateButton` when `home_io_control.lr1121_firmware_update:` is configured — hub-level options, not `switch:`/`button:` platform entries, so none can ever be confused with a device-bound `IOHomeSwitch`/`IOHomeCoverCommandButton` and each compiles to nothing (the LR1121 one behind `IOHOME_LR1121_FIRMWARE_UPDATE`) when its option is absent).
3. Runtime entities call into the hub through the port methods of `hub_ports.h` (`HubDevicePort`, `HubHeatingPort`, `HubControlPort`, which the hub implements), documented in [Controller Layer](https://laberning.github.io/home_io_control/group__hioc__hub.html).
4. The hub builds protocol frames using helpers from [Protocol Layer](https://laberning.github.io/home_io_control/group__hioc__protocol.html) and sends them through a concrete radio backend from [Radio Driver Layer](https://laberning.github.io/home_io_control/group__hioc__radio.html).
5. Replies, passive updates, and authenticated inbound messages are parsed back through the same protocol layer and merged into the shared device registry before the entity callbacks publish state to Home Assistant.

## Idle receive

While nothing else runs, the hub listens for one-way remotes and for reports a device sends on its own, and moves the receiver across the three hop channels. The channel changes every 2.7 ms (`HOP_TIME_US`), the dwell a short start preamble is sized for, so a remote's copies are heard whichever channel it uses. The hop is checked once per pass of the component's `loop()`, and ESPHome runs that pass only every 16 to 30 ms unless a component asks for more. The hub therefore holds a continuous-loop request (`HighFrequencyLoopRequester`) while its radio is set up and has not failed, decided by `decisions::wants_continuous_loop()`, so the hop runs on its own timer ([ADR 0086](adr/0086-the-idle-receiver-keeps-the-loop-running-so-its-channel-scan-follows-the-protocol-dwell.md)). A frame arriving, or a start preamble whose sync word is still to come, holds the channel. The preamble hold is one short slice that the receiver renews by restarting on the same channel while the preamble is detected again, up to a bound that covers a wake-up preamble, so a long preamble keeps the receiver to its sync word and a false detection parks it only briefly (`PreambleHold` in [radio_preamble_hold.h](../components/home_io_control/radio_preamble_hold.h), used by every driver). A radio that scans by itself ([ADR 0044](adr/0044-chip-neutral-transmit-intent-wake-level-idle-scanning-and-air-time.md)) is not hopped from the host, and exchanges, discovery and the key-extraction listen keep their own blocking waits. The cost is that the ESP32's loop task runs without sleeping between passes.

## Home Assistant Action Surface

Hub-level operations that should not become permanent entities are exposed through ESPHome native API actions: `rename_device`, `identify_device`, `identify_device_for`, `force_open_device`, `scan_paired_devices`, `oneway_set_position`, `oneway_remove_controller` and `heating_control`, plus the two diagnostic probe actions `probe_device` and `probe_sweep`, which exist only with `diagnostic_probes: true`. All share one data-driven descriptor class (`detail::ManagementServiceDescriptor` in `management_actions.cpp`), parametrized by action name, argument list, and callback — adding an action is one row in the registration table, not a new class. `scan_paired_devices` takes no arguments — it broadcasts a roll-call and reports every device that answers, rather than acting on one target device.

`IOHomeControlComponent` registers each descriptor with `api::APIServer` through its
`ManagementActions` collaborator, which then emits `esphome.home_io_control_action_result` so an
automation can inspect success and verification details. Home IO Control enables the required
native API compile-time flags internally, so user YAML only needs a normal `api:` block.

How to call each action from Home Assistant, with its fields and result event, is in
[Home Assistant actions](configuration/actions.md).

### Read Path

1. Every device-bound entity (cover, light, lock, switch, fan, climate, water heater) generates a companion diagnostic text sensor.
2. That sensor schedules a boot-time `GET_NAME` request through the hub's normal queued-operation path.
3. `CMD_GET_NAME_RESP` is decoded from Latin-1 wire bytes into cached UTF-8 text in the shared `IoDevice` record.
4. The same device callback fan-out used by the primary entities updates the generated text sensor in Home Assistant.
5. Name-request failures are isolated from movement/status behavior; unsupported devices keep an empty cached name.

### Write Path

1. Home Assistant calls the node-scoped native API action `esphome.<node_name>_rename_device`.
2. `ManagementActions` validates the supplied IO-homecontrol device ID and normalizes the requested UTF-8 name into the protocol's fixed Latin-1 payload.
3. The hub sends an authenticated `CMD_SET_NAME` exchange through the same radio/exchange stack used by other management operations.
4. A successful acknowledgement triggers an immediate `GET_NAME` readback so the cached `IoDevice.name` field stays authoritative.
5. The hub publishes `esphome.home_io_control_action_result` with success, verification, and any decoded device refusal metadata so the Home Assistant automation can react without requiring always-visible helper entities.

## Test Corpus

A versioned corpus of real captured IO-Homecontrol frames lives at
`tests/corpus/captures/<phase>/<id>.yaml`, one YAML file per scenario, `filename == id` and
`id = <subject>_<phase>[_<scenario>][_<chip>]` (naming convention + contribution workflow in
`tests/corpus/README.md`; the closed phase vocabulary and registered subject set are
`scripts/corpus/naming.py`). `scripts/corpus/build.py` renders the
YAML captures into a git-ignored C++ fixture header (`build/corpus/corpus_generated.h`) before
every host test build — the YAML is the single source of truth, so there is no generated file
to keep in sync or commit. `scripts/corpus/ingest.py` scaffolds new captures from pasted on-air
logs (and re-keys own-hardware captures with `--rekey` so no real system key is ever committed);
`scripts/corpus/validate.py` (`make corpus-validate`, part of `make lint`) enforces schema,
CRC/CTRL0 self-consistency, cryptographic promises, the naming convention (`filename == id`,
capture sits in its phase directory), and that every `tests/corpus/captures/<phase>/<id>.yaml`
path cited across the tree resolves. The `tests/corpus/corpus_*_test.cpp` host suites replay the
corpus through the real protocol/crypto/codec/decision/exchange code: frame parsing
(`corpus_frame_test.cpp`), crypto (`corpus_crypto_test.cpp`), decoding (`corpus_decode_test.cpp`),
classification (`corpus_classification_test.cpp`), exchanges (`corpus_exchange_replay_test.cpp`),
pairing (`corpus_pairing_replay_test.cpp`) and whole moves through the status poll policy
(`corpus_move_replay_test.cpp`), next to suites for one device family or rule each — an issue-derived capture
becomes a permanent parser/decoder regression fixture the day it's ingested.
